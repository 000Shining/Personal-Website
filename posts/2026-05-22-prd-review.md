## 1. 核心用户场景与未被满足的需求

### 核心场景

一个医疗器械公司的 RA 专员，周一早上收到任务——产品经理要在下周三前搞清楚：新产品如果要同时在中国和巴西注册，两边对生物相容性测试的要求有什么差异？

她目前的工作流是：

- 在共享盘里翻找去年存的 NMPA 指导原则 PDF（找了 20 分钟，发现不是最新版）
- 邮件里搜 ANVISA 的法规翻译件（邮件太多，搜不到）
- 打开 FDA 官网查同类产品的 510(k) 摘要作为参考
- 最后在 Word 里手工拼一份对比表

### 未被满足的需求（痛点）

| 痛点 | 本质 |
|---|---|
| 法规文档散落在共享盘、邮件、个人电脑、纸质档案；研发、注册、产品、市场部门使用不同信息来源； | **没有统一的知识库** |
| 文件名是乱码或编号，搜不到 | **缺乏结构化元数据管理** |
| 找到 PDF 后要逐页翻，几百页里找几段关键信息 | **没有语义检索能力** |
| 不知道这个文件是不是最新版本；法规变更、过渡期截止等关键时点依赖人工记忆 | **缺乏文档生命周期管理** |
| 横向对比多国法规全靠手动 Excel | **没有跨司法管辖区的对比能力** |
| 新人入职半年了还是不会查法规 —— 老员工的经验在脑子里 | **知识无法沉淀和传承** |
| FDA 公开数据在那放着，但没人会用 API 查 | **公开数据获取门槛高** |

**核心洞察：用户不缺法规文档，缺的是"在需要的那一刻，精准找到那段话，并知道它是否仍是有效的"。**

## 2. 成功指标定义

### 第一层：是否有人在用？（采用率）

| 指标 | 目标（3 个月） | 衡量方式 |
|---|---|---|
| DAU / MAU | 团队 80% 成员至少周活 | 页面访问日志 |
| 文档入库量 | 累计 200+ 份 | MongoDB 查询 |
| 问答请求量 | 日均 20+ 次 | qa_sessions 表 |
| 合集使用率 | 至少 3 个合集有文档 | collections stats |

### 第二层：用了有没有解决问题？（满意度）

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| 搜索命中率 | 首条结果相关率 > 85% | 人工标注抽样 |
| 问答"有用"反馈率 | > 80% | 聊天界面的 👍/👎 |
| 文档查找时间 | 从平均 20 分钟降到 < 2 分钟 | 用户访谈 / 计时测试 |
| NPS | > 40 | 季度问卷 |

### 第三层：对业务有没有价值？（转化）

| 指标 | 目标 | 衡量方式 |
|---|---|---|
| 注册准备周期缩短 | 减少 15% 的信息收集时间 | 项目里程碑对比 |
| 法规变更响应速度 | 从"被动知晓"变为 < 7 天主动更新 | 审批流程时间戳 |
| 注册文档一次通过率 | 因信息不完整导致的退审减少 | RA 团队反馈 |

**北极星指标：问答"有用"反馈率。** 如果用户问的法规问题能得到准确、带引用的回答，那就说明知识库、检索、生成三个环节都在正常工作。这是一个复合指标，驱动整个系统质量。

## 3. 关键决策与纠结

### 决策 1：向量存储 — MongoDB vs SQL

纠结过。MongoDB 做向量检索性能不如 SQL。但最终选了 MongoDB：

- **运维成本**：目标用户是中小型 RA 团队，不会有 DBA 或专门的向量数据库运维。多引入一个数据库 = 多一个故障点。MongoDB 已经存了所有文档数据，用同一个库做向量存储意味着只需要维护一套基础设施。
- **规模预估**：当时预估文档量在几百到几千份，每份产生几十个 chunk。总共几万个向量，MongoDB 做暴力余弦搜索完全够用。
- **如果重新选**：文档量超过 1 万份后，可能会迁移到 MongoDB Atlas Vector Search（支持原生 kNN），或者评估 Qdrant 轻量部署。

### 决策 2：OCR — PaddleOCR vs Tesseract

纠结程度中等。PaddleOCR 中文识别率明显优于 Tesseract，但 PaddlePaddle 安装包巨大且依赖复杂。最终选了 PaddleOCR：

- 这个系统的主要文档来源是 NMPA（中国），中文 OCR 质量是刚需。
- 做了一个 fallback 设计：OCR 初始化失败不会阻塞文档上传，PyMuPDF 能提取文本的优先用它。
- **代价**：部署时 PaddlePaddle 经常因为版本不兼容装不上。如果重来，我会把 OCR 做成可选服务，用 Docker sidecar 隔离，不影响主服务启动。

### 决策 3：LLM — DeepSeek vs GPT-4 vs 通义千问

做了评估对比：

| 维度 | GPT-4 | DeepSeek | 通义千问 |
|---|---|---|---|
| 中文法规理解 | 一般 | 强 | 强 |
| 英文法规理解 | 强 | 较强 | 一般 |
| API 成本 | ~$0.03/K tokens | ~$0.002/K tokens | ~$0.008/K tokens |
| 数据合规 | 敏感（非中国部署） | 国内合规 | 国内合规 |

DeepSeek 是性价比和数据合规的平衡点。但设计上留了后路——用的 OpenAI 兼容接口，换模型只需改 `base_url` 和 `model` 配置。

## 4. 如果重新写这份 PRD，我会改进什么

### 改进 1：用"用户故事"替代"功能列表"

现在的 PRD 是系统功能清单（DOC-001、DOC-002...），虽然完备但缺少叙事。重写会用这种格式：

> **故事 3：按司法管辖区筛选**
> *作为 RA 专员，我想只搜索 NMPA 相关的文档来回答关于中国注册的问题，这样我不会被日本 PMDA 的法规结果干扰。*
>
> **验收标准：**
> - 对话中可选择一个合集进行筛选
> - 筛选后仅检索该合集的文档块
> - 切换合集时保留对话上下文

### 改进 2：增加"不作为"清单（Out of Scope）

PRD 写得越全，越容易让人以为这些都要做。重写时会加一个明确的 Out of Scope 表格：

| 不做的事情 | 原因 |
|---|---|
| 法规自动翻译 | 翻译质量不可控，合规风险高；用户更信任人工翻译 |
| 合同/商务文档管理 | 这是 RLD 系统的事，不要扩张边界 |
| 临床试验数据管理 | 那是 CTMS 的范畴 |
| 移动端 App | V1 只需桌面端响应式 |

PRD 的价值不仅在于说"要做什么"，更在于说"不做什么"，防止范围蔓延。

### 改进 3：性能门禁写进需求

现在 PRD 的非功能需求只列了数字（< 15s），但没有写清楚什么情况下这个 15 秒不适用。重写时会加：

> **性能门禁：**
> - 问答 P95 延迟 < 15s，P99 < 30s
> - 超标场景：用户上传的 PDF 超过 200 页时，OCR 处理时间不在此门禁范围内
> - 每周运行一次自动化性能回归测试（预置 20 个问题，记录延迟分布）

### 改进 4：补充合规与隐私需求

作为医疗监管领域的工具，PRD 里应该有一整节讲数据合规：

> **合规需求：**
> - 用户上传的未公开法规翻译件是否涉及版权？——需法务评估，系统层面做访问日志记录
> - QA 历史数据保留策略：默认保留 90 天，支持管理员手动清除
> - 如果使用 DeepSeek，需在隐私政策中说明用户问题会传输到第三方 API

### 改进 5：先定义"成功用户体验"，再定义功能

当前 PRD 从功能出发。重写时先写 3 个关键的用户旅程：

1. **"第一天入职的 RA 新人"** — 怎么从 0 开始找到自己需要的法规
2. **"日常查询的主力 RA"** — 每周 5 次以上的高频问答场景
3. **"写注册申请报告的人"** — 需要深度阅读文档并摘录引用

功能需求从这些旅程里自然生长出来，而不是先列功能再想用户。
